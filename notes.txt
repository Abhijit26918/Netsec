1. WHAT THIS PROJECT IS
----------------------------------------------------------------
An end-to-end MLOps pipeline that classifies whether a URL is
phishing or legitimate, based on 30 handcrafted features
(having_IP_Address, URL_Length, SSLfinal_State, etc).

Flow:
  MongoDB Atlas (raw data)
      -> Data Ingestion      (pull from Mongo, train/test split)
      -> Data Validation     (schema check + KS-test data drift)
      -> Data Transformation (KNN imputer, fit on train only)
      -> Model Trainer       (GridSearchCV over several classifiers,
                              picks best by test accuracy)
      -> final_model/{model.pkl, preprocessor.pkl}
      -> FastAPI dashboard   (train live + predict on uploaded CSVs)

7. MODEL CANDIDATES (model_trainer.py)
----------------------------------------------------------------
Trained + compared via GridSearchCV (3-fold CV), best picked by
test-set accuracy: Random Forest, Decision Tree, Gradient Boosting,
Logistic Regression, AdaBoost, and XGBoost.

XGBoost is toggleable — at the top of components/model_trainer.py:
    INCLUDE_XGBOOST = True
Set it to False to exclude XGBoost from the comparison/training
run without touching any other code (models/params dicts only add
XGBoost's entries when this flag is True).

Last run's result, all 6 candidates (2026-09-12, 16:57:52):
    XGBoost              97.01%  <- winner, saved to final_model/model.pkl
    Random Forest         96.97%
    Decision Tree          96.52%
    Gradient Boosting       95.57%
    AdaBoost                 92.36%
    Logistic Regression      92.09%
(XGBoost and Random Forest are within ~0.04% of each other — this is
close enough that which one "wins" can flip between runs, since
train/test split and GridSearchCV both have randomness. Good
interview point: a tiny accuracy gap isn't necessarily meaningful —
mention run-to-run variance if asked to justify the pick.)

8. BUGS FOUND & FIXED VS. THE ORIGINAL (2-years-ago) PROJECT
   -- good interview talking points --
----------------------------------------------------------------
- exception.py: `raise NetworkSecurityException` with NO arguments
  in a couple of except blocks -> would crash with a bare TypeError
  instead of the custom exception. Fixed to always pass (e, sys).

- data_validation.py: DataValidationArtifact pointed
  valid_train_file_path at the ORIGINAL ingestion file path, not
  where the validated CSV was actually written -> downstream
  stages could silently read stale data. Fixed to point at the
  real validated-file path.

- data_validation.py: KS-test drift_status was a raw numpy.bool_
  object, which PyYAML serializes as an unsafe `!!python/object`
  tag -> yaml.safe_load() (used elsewhere in this project) would
  outright refuse to read it back. Fixed by casting to a plain
  Python bool(). (Talking point: never use yaml.load on untrusted
  input, always safe_load — this is exactly the vulnerability class
  that causes.)

- model_trainer.py: model selection used r2_score (a REGRESSION
  metric — how well continuous predictions fit) to pick the best
  CLASSIFIER. Switched to accuracy_score, which is the correct
  metric family for a classification task.

- model_trainer.py: `save_object(path, obj=NetworkModel)` saved the
  CLASS itself, not the trained `Network_Model` INSTANCE -> loading
  it back and calling .predict() would have failed. Fixed to save
  the actual instance.

- app.py: `templates.TemplateResponse("table.html", {"request":...})`
  used the old Starlette API. Newer Starlette requires `request` as
  an explicit first positional argument (not inside the context
  dict), because the context participates in a cache-key lookup and
  dicts aren't hashable. Fixed to
  `templates.TemplateResponse(request, "table.html", {...})`.

- app.py /predict: didn't defend against a user re-uploading a CSV
  that still has the "Result" (label) column -> scikit-learn's
  strict feature-name validation would 500. Fixed to auto-drop the
  target column if present (defensive coding at a user-facing API
  boundary — this is more real-world robustness than the original
  had).

9. KEY CONCEPTS TO BE ABLE TO EXPLAIN (interview prep)
----------------------------------------------------------------
- Custom Exception pattern: wraps sys.exc_info() to capture exact
  file + line number of failure, standard for multi-stage pipelines.

- Config vs Artifact pattern:
    Config  = WHERE to read/write + what params (decided upfront)
    Artifact = WHAT a stage produced (paths/metrics), fed into the
               NEXT stage's inputs
    Every run is isolated under Artifacts/<timestamp>/... so nothing
    from run N overwrites run N-1.

- Data drift detection: Kolmogorov-Smirnov 2-sample test per column,
  comparing train vs test distributions. p-value < 0.05 => distributions
  differ significantly => drift flagged for that column.

- Why fit the KNNImputer/preprocessor ONLY on train, then just
  .transform() on test: avoids data leakage (test-set information
  influencing preprocessing, which would make evaluation optimistic).

- GridSearchCV with cv=3: for each hyperparameter combo, trains on
  2 folds / validates on the 3rd, three times, averages the score —
  tunes hyperparameters without ever touching the true held-out
  test set.

- Why MongoDB in the loop at all instead of reading the CSV
  directly: simulates a real production setup where raw data lives
  in a continuously-updated database; ingestion's job is "pull the
  current snapshot," decoupling the pipeline from data's origin.

- Server-Sent Events (SSE) vs WebSockets for the live dashboard:
  SSE is one-directional (server -> browser), simpler than
  WebSockets, and exactly fits "stream progress updates" — no need
  for the browser to send anything back mid-stream.

- Why ship a Docker IMAGE instead of having the server `git pull` +
  `pip install` on every deploy:
    * Environment drift — the server's Python/OS packages must stay
      identical to dev forever; an image freezes the exact filesystem.
    * No atomic rollback with git+pip (old dependency versions may
      not resolve the same way later); rolling back an image is just
      running the previous tag, instantly, guaranteed identical.
    * What's tested in CI is bit-for-bit what runs in prod (no risk
      of pip resolving different transitive versions at deploy time
      than it did during testing — matters a lot here since
      final_model/model.pkl was pickled with a specific scikit-learn
      version).
    * Scales to N servers identically — build once, `docker pull`
      everywhere, instead of repeating setup per machine.

- The CI/CD chain (GitHub push -> running on EC2), concretely:
    1. `git push` triggers a GitHub Actions workflow automatically.
    2. Job "integration" (CI) runs on a GitHub-hosted runner (a
       temporary VM GitHub spins up and destroys after the job).
    3. Job "build-and-push-ecr-image" — ALSO a GitHub-hosted runner —
       runs `docker build` (using our Dockerfile) then `docker push`
       to AWS ECR (a private image registry; just storage).
    4. Job "Continuous-Deployment" runs on a SELF-HOSTED runner —
       this is EC2 itself. A small GitHub Actions Runner agent is
       installed on EC2 once (systemd service) and continuously polls
       GitHub for jobs — EC2 reaches out to GitHub, not the other way.
       When this job fires, EC2's own agent runs `docker pull`
       (from ECR, using EC2's own AWS creds) then `docker run` to
       restart the container with the new image.
    Net result: EC2 never runs `git pull` or `docker build` at all —
    it only ever pulls finished images from ECR. The only manual
    human step in the whole chain is the original `git push`.
    (Alternative to self-hosted-runner, simpler for smaller projects:
    a GitHub Action that just SSHes into EC2 and runs commands
    remotely, e.g. the `appleboy/ssh-action` action — no persistent
    agent needed. This project follows the self-hosted-runner
    pattern since that's what the original tutorial used.)

10. DOCKER
----------------------------------------------------------------
Dockerfile walks through (see Dockerfile in project root):
  FROM python:3.10-slim              matches venv's Python version
  WORKDIR /app
  COPY requirements.txt setup.py ./  copy manifest first...
  COPY networksecurity ./networksecurity   ...and the package "-e ." needs
  RUN pip install -r requirements.txt      (cached unless these change —
                                             editing app.py/templates later
                                             won't force a reinstall)
  COPY . .                           now bring in everything else
  RUN useradd ... && chown -R appuser /app  don't run as root
  USER appuser
  EXPOSE 8000
  CMD ["python", "app.py"]

.dockerignore excludes venv/, logs/, Artifacts/, .env, __pycache__/,
etc. — final_model/{model.pkl,preprocessor.pkl} IS included, so a
container can serve /predict immediately without retraining.
Secrets (MONGO_DB_URL, AWS keys) are NEVER baked into the image —
passed at `docker run` time via -e flags or --env-file.

Commands used, in order:

  Build the image:
    docker build -t networksecurity:local .

  Run it locally (mongo creds needed only for /train, not /predict):
    docker run -d -p 8000:8000 --env-file .env --name networksecurity-test networksecurity:local

  Check it's not running as root:
    docker exec networksecurity-test whoami        -> should print "appuser"

  View logs / stop / remove:
    docker logs networksecurity-test
    docker stop networksecurity-test
    docker rm networksecurity-test

  Push to Docker Hub (public registry — anyone with Docker can pull
  and run this; the app's /predict works instantly since the trained
  model is baked in, no MongoDB needed unless they hit /train):
    docker login
    docker tag networksecurity:local chikati/networksecurity:latest
    docker push chikati/networksecurity:latest

  Anyone can then run it with zero setup:
    docker pull chikati/networksecurity:latest
    docker run -p 8000:8000 chikati/networksecurity:latest

CMD vs ENTRYPOINT: CMD (what we use) is a default that
`docker run image <other-command>` can override entirely.
ENTRYPOINT is for when extra `docker run` args should be APPENDED
instead of replacing the command — matters more for CLI-tool-style
images than a single-purpose web app like this one.

Volumes: not used here. Artifacts/logs live in the container's
writable layer and vanish when the container is removed (except
final_model/, baked in at build time). S3 sync (AWS phase) is our
actual persistence layer across runs/machines — chosen over a Docker
volume because it also needs to work from EC2, not just locally.

docker-compose: not needed — only one container exists (MongoDB is
external, on Atlas, not something we run ourselves). Compose earns
its keep when you're orchestrating 2+ containers together.
